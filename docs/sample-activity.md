# Sample activity

3,278 labelled sample accounts, with quiz results, arguments, revisions,
challenges, counterpart exchanges, reading answers and classes from
2026-09-18 on, rendered through the ordinary pages, and new arguments every
six hours for as long as the run lasts. Nothing here is a demo page: the
rows sit in the real tables, marked, and every page that can show one says
what it is.

Arthur's ruling of 2026-11-04 shapes it: 3,278 accounts, permanent until
he says otherwise, generated by a scheduled GitHub Actions workflow, "Sample"
on every surface a sample appears, no synthetic referrers, nothing in
PostHog, real numbers kept real, a reader's own rating, percentile and
streak computed against real readers only, class pages that never show a
sample, exact duplicate arguments under 5%, and readers' data never leaving
Supabase.

The code is `scripts/seed/`, `scripts/seed-ci.ts` (the workflow's entry
point), `scripts/seed-production.ts`, `scripts/unseed-production.ts`,
`scripts/seed-local.ts` and `scripts/unseed-local.ts`; the schema is
`supabase/migrations/0023_sample_activity.sql`; the workflow is
`.github/workflows/sample-activity.yml`.

## Where a sample account can be seen

The site has no public profile, no per-person leaderboard and no
messaging, so a sample account is seen in fewer places than the word
"accounts" suggests.

| Surface | Who can see it | What a sample shows |
| --- | --- | --- |
| `/table` (school table) | anyone | Counted like anyone else in the week it falls in. In any week with a sample argument or school change the table says "This week's table includes sample accounts." and links here. |
| `/today` school rank | signed-in readers | The school's place on the same table, with "This week's ranks include sample accounts." and the same link. |
| `/debate/<slug>/<id>` (verdict) | anyone with the link | The Sample label; "Sample assessment" in place of "How the judge scored you", and a line saying the judge did not read it. No share row. Page title "Sample verdict". |
| its link preview (`opengraph-image`) | anyone shown the link | A "Sample assessment" mark beside the score. |
| `/r/<id>` (result) | anyone with the link | The Sample label, "A sample account's result", the stranger's view only. Page title "<School> · Sample". |
| its card (`opengraph-image`, `card.png`) | anyone shown the link | A "Sample" mark above the quotation. |
| `/c/<id>` (challenge) | anyone with the link | The Sample label, "A sample account's challenge"; "Take the quiz" goes to `/quiz` without accepting it. Page title "A sample account's challenge". |
| its link preview | anyone shown the link | The challenger's result card (`/r/<id>/opengraph-image`) with its "Sample" mark; no image if the challenger's result is not a sample, or if the card's lookup fails. |
| `/class/<code>` | the class owner only | Never a sample: a reader's class cannot hold one, and the page leaves out any sample member whatever the data says. |
| `/counterpart/<id>` | the two participants only | Sample exchanges are between sample accounts only. |
| `/me` | the reader only | Nothing of a sample's. |

No page links to a sample's verdict, result or challenge, and none is in
the sitemap. The table and Today count the current ISO week, and the
workflow adds the activity since its last run every six hours, so samples
are part of every week's table, not only the first.

The label (`src/components/sample/SampleLabel.tsx`) is a `<details>`: it
reads "Sample" and opens to "An illustrative account with generated
activity, not an active member. It does not respond to messages or
challenges." `/method#samples` explains the rest.

## What a sample can never touch

- **A reader's own numbers.** Rating: `/api/judge` computes a topic's par
  from the last 50 genuine originals (`.eq("is_sample", false)`), and
  `recordChallengeDebate` returns early when either side of a challenge
  is a sample, so no sample moves a reader's rating. Percentile:
  `elo_percentile` counts genuine profiles only ("Higher than N% of
  debaters" on `/me`). Streak: a reader's own days, untouched. The
  generator replays sample ratings against a par of its own and never
  writes `debate_topics`. The only standing that includes samples is the
  school table's order, shown on `/table` and as a school's place on
  Today, both with the note; the site has no per-person rank.
- **Analytics.** PostHog never receives anything from a page showing a
  sample's verdict, result or challenge: such a page renders
  `SamplePageMarker`, and `src/lib/analytics/client.ts` checks for it
  twice. `track()` returns before loading PostHog, so `page_viewed`,
  `verdict_viewed`, `card_viewed`, `challenge_viewed` and the rest are not
  sent; and PostHog's `before_send` drops whatever PostHog would send by
  itself while the marker is on the page (autocapture, `$identify`, web
  vitals), since PostHog stays loaded when a reader moves from a genuine
  page to a sample one. The project has session replay, heatmaps and
  dead-click capture on (read from PostHog on 2026-11-04), and those send
  in batches, sometimes after the reader has left: `before_send` also
  drops any event carrying a sample page's address and any replay chunk
  recorded while one was open, and replay is paused for as long as a
  sample page is open. A visit that starts on a sample page does not load
  PostHog at all; the reader is identified on their first genuine page.
  `tests/seed/analytics-sample.test.ts`. The seed writes
  rows directly and emits no event. Sample quiz results carry no
  referrer. A page showing a sample passes no referrer on (`referrer:
  "no-referrer"` in its metadata, `SAMPLE_PAGE_REFERRER` in
  `src/lib/sample.ts`; `docs/decisions.md`, "Arthur's rulings of
  2026-11-05 on Checkpoint A", 18), so a page opened from one does not
  report the sample page's address: not in `document.referrer`, which
  reaches PostHog's `page_viewed` and is stored on a reader's own quiz
  result, and not in the Referer header, which `/r/[id]` reads into
  `card_viewed` and `share_page_viewed`. The root layout states the
  browsers' default for every other page, which puts it back after a
  client-side navigation away from a sample page
  (`tests/seed/sample-referrer.test.ts`). One gap: Next.js streams
  metadata to browsers after the page's content, so a click made before
  that part arrives and before the page hydrates is a full load without
  the policy yet.
- **Matching.** No sample argument has `seeking_counterpart_at` set, so
  `seekCounterpart` never offers one to a reader.
- **Challenges.** A sample never answers. A reader who opens a sample
  challenge takes the quiz without accepting it, and `submitQuizResult`
  treats a sample challenge as no challenge even when the link is made by
  hand. `createChallenge` only opens a challenge from the caller's own
  result, which a sample's never is.
- **References.** No reader can attach a row of their own to a sample row,
  even with an id worked out from the public generator. A trigger in 0023
  refuses it on every path a signed-in or anonymous request has through
  the Data API: joining a sample class or adding a sample member, a
  challenge or quiz result pointing at a sample's result or debate, a
  debate whose parent or challenge is a sample's, a block naming a sample
  account, a report on a sample exchange's turn. A genuine challenge
  naming a sample row is refused whoever writes it. So no genuine row can
  come to depend on a sample row, and teardown is never left choosing
  between the two (`scripts/test-0023-sample-activity.sh` tries each path).
- **Email and sign-in.** Sample users are created through the Auth admin
  API with `email_confirm: true` (no confirmation mail), no password, a
  ban of 876,000 hours, and addresses on `sophecs.test`, a domain reserved
  never to resolve. Supabase Auth refuses requests that relate to a banned
  user. No invitation, link or reset is ever requested.
- **Spending.** No model is called. Every sample verdict is a template,
  `prompt_version` `sample-template-1`, `verdict_is_template` true. No
  `ai_calls`, `reports`, `blocks`, payment or analytics row is written.

## Real numbers

Every user and activity figure the site shows a reader is their own, or
genuine-only (the percentile). PostHog holds no sample event. Any count
taken from the database must filter on the marker; this query, run in the
Supabase SQL editor, reports real and sample side by side:

```sql
select 'accounts' as what,
       count(*) filter (where not coalesce((raw_app_meta_data->>'sophecs_sample')::boolean, false)) as real,
       count(*) filter (where coalesce((raw_app_meta_data->>'sophecs_sample')::boolean, false)) as sample
  from auth.users
union all select 'profiles', count(*) filter (where not is_sample), count(*) filter (where is_sample) from profiles
union all select 'quiz results', count(*) filter (where not is_sample), count(*) filter (where is_sample) from quiz_results
union all select 'arguments', count(*) filter (where not is_sample), count(*) filter (where is_sample) from debates
union all select 'arguments this week', count(*) filter (where not is_sample), count(*) filter (where is_sample)
  from debates where created_at >= date_trunc('week', now())
union all select 'challenges', count(*) filter (where not is_sample), count(*) filter (where is_sample) from challenges
union all select 'exchanges', count(*) filter (where not is_sample), count(*) filter (where is_sample) from exchanges
union all select 'reading answers',
       count(*) filter (where p.id is null or not p.is_sample), count(*) filter (where p.is_sample)
  from reading_responses r left join profiles p on p.id = r.user_id
union all select 'classes',
       count(*) filter (where p.id is null or not p.is_sample), count(*) filter (where p.is_sample)
  from classes c left join profiles p on p.id = c.owner_id;
```

`scripts/review-verdicts.ts` reads genuine verdicts only.

## The marker and the registry (migration 0023)

- `is_sample boolean not null default false` on `profiles`,
  `quiz_results`, `debates`, `challenges` and `exchanges`, and
  `debates.verdict_is_template`. Existing rows read false without being
  rewritten.
- Eleven triggers. Five (`*_guard_sample`) let only the server role set or
  clear the marker. Six (`*_guard_reference`, on `class_members`,
  `challenges`, `quiz_results`, `debates`, `blocks` and `reports`) refuse
  an anonymous or signed-in write that would point at a sample row, and a
  genuine challenge naming a sample row whoever writes it. The function
  behind them runs as its owner so it can see sample rows the caller
  cannot, and no client role may call it directly.
- `seed_runs`: one row per run, with a hash of its fixed inputs (never the
  seed), the generator version, the base window (`window_from`,
  `base_to`), how far its activity reaches (`window_to`, which moves
  forward with each extension), status, lock, counts and the last run's
  full report (`last_report`). `seed_run_items`: one row per row a run
  intends to write, recorded before the write; a unique index on
  `(kind, row_id)` means two runs can never own one row. Both tables are
  readable and writable by the server role only.
- `debates_public` and `public_results` gain the marker, appended, with
  their owner and grants unchanged.
- An index on `debates(created_at)` for the week reads.
- The rollback refuses while any sample row remains, any run is not torn
  down, or any registry item is still intended or created.

`scripts/test-0023-sample-activity.sh` proves all of it on a throwaway
local database, including the rollback and re-apply.

## The dataset

Two layers, both from one secret seed:

- **The base window**, from 2026-09-18 to the moment the run starts
  (`base_to`): 3,278 accounts, 4,917 anonymous quiz results, 328
  challenges, 492 counterpart exchanges, 10 classes, reading answers, and
  the accounts' arguments. Fixed for the life of the run.
- **Extensions**, every six hours after that: the arguments and revisions
  of the accounts still active. No new accounts arrive; most stop within
  a fortnight of joining, regulars within weeks, and heavy users (3% of
  accounts) stay for months, so activity thins slowly. Adding arrivals
  would be a decision for Arthur.

Each debater's arguments come from their own random stream and stop at
their own lifetime, never at the window's end, so moving the end later
only appends: every row up to the old end comes out the same, ids
included (`tests/seed/extension.test.ts`). What changes in an earlier row
is a profile's rating, streak and school, which the engine updates.

What the generator reuses from the app rather than reimplementing: the
quiz bank and `scoreQuiz` (answers are biased by a leaning; the school
comes out of the answers), `soloElo`, `pairwiseElo` and `applyStreakDay`
in time order, `checkQuote` and `checkBody` for every turn,
`getWeeklyMotion`, `authorForSeq`, and the seven-day topic lock and
five-a-day limit `/api/judge` enforces.

**Arguments.** Composed from hand-written passages in
`scripts/seed/arguments/fragments/`: four positions, four reasons, three
examples and two objection-and-answer passages per motion and school, five
weak passages per motion, four closings per school, and six opening
sentences. `scripts/seed/compositions.ts` lists every composition the
passages allow for a motion, school and tier that lands between 80 and
250 words (about 170,000 in all), shuffles each list once per run, plain
compositions before the ones with an opening sentence, and gives them out
in time order. No composition is used twice until its list runs out, so
exact duplicates stay near zero; near duplicates (the same composition with
another opening, closing or example) are measured and reported. The banks
(`arguments/<topic>.<school>.json`, forty each) are a reviewable sample of
the same compositions.

Measured on a plan with the defaults and a test seed, base window to
2026-11-04 09:00 UTC:

**Verdicts.** The judge's own response shape, validated in the tests
against `VerdictSchema`. The score is `10 x (0.5 F + 0.25 R + 0.25 E)`
plus at most 2 points of noise, held in the tier's range (strong 70-90,
mid 50-70, weak 25-50). The strongest and weakest moves quote the
argument verbatim. The named objection is the rival whose objection the
argument does not answer, and a revision adds that answer.

## How it runs

`.github/workflows/sample-activity.yml` runs `npm run seed:ci` on main,
every six hours at minute 41, and by hand from the Actions tab. It never
runs on a push or a pull request, and its secrets belong to the GitHub
environment `sample-activity`, which only main may use, so no fork, branch
or other workflow can reach them (`tests/seed/isolation.test.ts` checks the
triggers and the environment).

Every six hours rather than weekly: a sample row is never dated in the
future, and the table shows only the current week, so a weekly run would
leave each week's table without samples until its next run.

The modes (`scripts/seed/ci.ts`):

- `canary`, by hand: starts a run, base window to now, the first 40
  accounts and what depends only on them. Refused while a run exists.
- `full`, by hand: the rest of that run, and its activity up to now.
- `extend`, the schedule: the run's activity up to now. Does nothing until
  a full stage has passed, or after teardown.
- `teardown`, by hand, on Arthur's instruction only (see Teardown).

Each run makes its plan in memory from the run's fixed inputs and the
secret seed, runs the dry-run checks (reads only), executes, and
validates. Workflow logs are public, so the log holds counts, timings and
check names with ok or FAIL, and nothing about readers, no hash and no
seed; the full report, genuine figures included, goes to
`seed_runs.last_report` (`tests/seed/ci.test.ts` checks the log).

## Credentials

The workflow writes `.env.seed.production` from two secrets of the
environment `sample-activity`, with owner-only permissions, and removes it
whatever happens. Environment secrets, not repository secrets: a
repository secret can be read by a workflow on any branch pushed to the
repository, and branches are pushed here routinely. Set up once, in
GitHub, Settings, Environments, New environment `sample-activity`;
Deployment branches and tags: Selected branches, add `main`; then add the
two as environment secrets there (and none as a repository secret):

- `SEED_SUPABASE_SERVICE_ROLE_KEY`: the project's service key (Supabase,
  Project Settings, API keys: the `service_role` key, or a secret key
  `sb_secret_...`).
- `SEED_PLAN_SEED`: 24 to 128 letters, digits, `-` or `_`, for example the
  output of `openssl rand -hex 16`. With the generator public, the seed
  fixes every id the run will write, so it is never printed, never
  committed and never stored in the database.

The URL is not a secret and is written by the workflow. Locally,
`.env.seed.local` (`SEED_LOCAL_DATABASE_URL`, on 127.0.0.1 or localhost)
is the only file read. Nothing reads `process.env`, `.env.local` or
`.env.production`. The production URL must be exactly
`https://<ref>.supabase.co` for the ref given twice; a JWT key must be a
`service_role` key issued for that ref.

## How a run writes

In foreign-key order (auth users, profiles, quiz results, challenges,
debates, challenge links, exchanges, turns, reading answers, classes,
members), in batches. For each batch: record intents in the registry;
insert with insert-or-ignore on the primary key; read every row back and
check it is marked or owned by the run's users (a row that exists and is
not the run's stops the run rather than be adopted); mark the intents
created. Then the profiles already written are read back and compared with
the plan, and the ones whose rating, streak or school has moved are
updated, scoped to sample rows. A run whose plan has another seed, base
window or config is refused, and so is a plan that ends before the run
already does.

One run at a time: the workflow's concurrency group, and a lock in
`seed_runs` that a run refreshes before every batch and about once a
minute while it creates auth users. A lock untouched for 15 minutes
belongs to a process that died and can be cleared. In the workflow a run
clears one itself (a job the runner killed, by the timeout, a cancel or a
lost machine, leaves its lock behind), which is safe there because the
concurrency group runs one job at a time; from a machine it takes
`--break-stale-lock`.

## Teardown

One step, run only on Arthur's instruction. From the Actions tab: "Sample
activity", mode `teardown`, with the run's id typed into
`confirm_teardown`; it refuses without the exact id. Or, from a machine
with the service key:

    npm run unseed:production -- --expected-project-ref tekifezydjlgxgndkxul --confirm-production tekifezydjlgxgndkxul --run-id <id>
        # preview: what would go, and any genuine row that points at a sample row
    ... --execute --confirm-teardown <id>

It works from the registry, so no plan is needed. It deletes the run's
registry items in dependency order, scoped again by the marker or the
run's own users, clears a genuine row's nullable reference to a sample row
first, and stops on anything it could only keep by deleting it. It keeps
the run and its registry rows, marked deleted, as the audit record, and
never restores old state. The workflow's log gets counts only; row ids go
to `seed_runs.last_report`. After teardown the schedule does nothing;
disabling or deleting the workflow ends it.

## Backup and recovery

Production is on the free plan, with no restorable backup. The recovery
path does not need one: every sample row is in the registry and removable
by id, and the run never writes a genuine row (every row is read back and
must be marked or owned by the run, and every update is scoped to the
marker). Readers' data never leaves Supabase: there is no export, and the
checks read counts, the topics, and each topic's par window, which is the
ratings alone, by the query `/api/judge` makes for the par; no reader's
id or row reaches the runner for them. Teardown, run only on Arthur's
instruction, is the exception: to find genuine rows that point at a
sample row it reads the reference columns (ids) of the tables involved
into the runner's memory, and keeps any it finds in
`seed_runs.last_report`, not the log. The reports a command writes to
disk leave out the baselines.

Validation fails only on checks that hold whatever readers do: each
topic's stored par must equal the par computed from genuine originals
alone (or be unchanged where there are none), and `elo_percentile(1200)`
must equal the share computed from genuine profiles alone. A failing
check is read again five seconds later before it is reported. Two
judgings finishing together on one topic can leave its par off until the
next judging there; a par check that fails twice is a stop either way.

## Rollout

Each step only after the one before has passed:

1. Security advisor before; apply `0023_sample_activity`; read back the
   columns, the registry tables (RLS on, no client grants), the eleven
   triggers, the two views and `elo_percentile(1200)`; advisor after. Any
   new ERROR stops here.
2. Merge the pull request; confirm the merge commit and that the
   production deploy is Ready.
3. Arthur creates the environment `sample-activity`, limited to main, and
   adds the two secrets to it (Credentials).
4. Actions tab, "Sample activity", run with `canary`. Read the log and
   `seed_runs.last_report`; fetch a sample verdict, result and challenge
   page and their images.
5. The same with `full`.
6. From then on the schedule runs `extend` every six hours.

## At launch

Quiz v2 ships at launch, and a run cannot outlive a change to the quiz,
the motions or the passages (Limits). Arthur, 2026-11-05: "plan the
sample teardown and a fresh run into the launch steps". In order:

1. **Teardown, on Arthur's instruction, before the launch merges.**
   Actions tab, "Sample activity", `teardown`, with the run's id typed
   into `confirm_teardown`. It passes when that first teardown job is
   green. It stops, with "teardown stopped" in the log, if it would delete
   a genuine row or leave any of the run's rows behind, and the job also
   goes red if the par or percentile checks after the deletes fail. A
   second teardown reports "nothing to tear down" and is green either
   way, so only the first one counts. The genuine counts in the report are
   for information: readers may add or delete rows meanwhile. Teardown has
   no rollback (Teardown), and every existing sample link ends here. Doing
   it first means no scheduled `extend` runs against the changed quiz.
2. **The launch merges**, and its production deploy is confirmed Ready.
3. **A fresh run:** `canary`, then `full`, as in Rollout steps 4 and 5,
   each with Arthur's go-ahead. The new run has a new id (the canary's
   start time), and the schedule extends it once its full stage has
   passed.

## Stop conditions

Stop and report, without retrying past the engine's own retries, if:

- any validation check fails, exact duplicate argument texts reaching 5%
  among them;
- the run refuses to adopt a row;
- auth user creation is refused, or any created user comes back without
  its ban;
- the dry-run checks find the motions differ, another run holds a lock,
  or the plan is not the run's;
- the canary's rate puts the full run beyond an hour.

A failed validation halts the run: `seed_runs.status` becomes `failed`
with `last_error` starting "halted: validation failed", and from then on
each scheduled run writes nothing and fails, until a `full` stage run by
hand passes validation again. Any other failure (a lost runner, the
timeout, a database error) is retried by the next scheduled run, which
resumes. A run that keeps failing shows as failed runs in the Actions
tab, and GitHub emails the account that set the schedule.

## Limits

- No new accounts arrive after the base window, so weekly activity slowly
  falls as heavy users' lifetimes end.
- GitHub turns off a public repository's scheduled workflows after 60 days
  with no commit; a commit, or re-enabling it in the Actions tab, turns
  it back on.
- Streaks use UTC days, as the app does.
- Exact duplicates rise once a composition list runs out. Measured in
  review on 2026-11-04 at production volumes: 0.02% at the start, 0.28%
  after 90 days, 3.29% after a year and 9.85% after two, so the 5% check
  halts the run after about 16 months unless the passages grow. Making
  the plan takes 14 s at the start and about 3 minutes after a year.
  Re-measured on 2026-11-05 with two other seeds and production's base
  window: 0.2% at the start, 0.5% and 0.7% after 90 days, 3% after a
  year. The start is higher than the 0.02% above, the year about the
  same, so the 16-month estimate stands. The production run's own check
  read 0.3% after its full stage.
- The motions, the passages and the quiz are fixed for the life of a run.
  Each motion's text is part of the run's base hash, so rewording, adding
  or retiring a motion makes every later run refuse at the dry run,
  writing nothing. An edit to the passages changes the texts planned for
  rows already written, which the spot checks then fail on, halting the
  run. The generator replays the live quiz questions and `scoreQuiz` to
  give each sample its school, so a change to the quiz (Quiz v2, for one)
  changes the planned schools of rows already written, which the spot
  checks also fail on. In every case the way on is teardown and a new
  run, which ends every existing sample link. Say before changing any of
  them while a run is live.

## Decisions taken

Arthur's ruling of 2026-11-04 settled the open items: the wording
("Sample", "Sample assessment", `/method#samples`), the class names and
the reading answers are accepted; labelled generated arguments are an
accepted exception to "no invented copy"; the school table may include
samples with its note; no synthetic referrers; no genuine-row export. The
argument passages (`scripts/seed/arguments/fragments/`) and the template
verdict wording (`scripts/seed/verdicts.ts`) stand as they were approved
with the run.

## Findings from building this

Three bugs found here were fixed in their own pull requests on 2026-11-04:
a challenge could not be accepted (#59), no counterpart exchange could
take its first turn (#58), and anyone could open a challenge in another
reader's name (#60). The school table and Today read a week of debates
and every profile's school history without a range, so above 1,000 rows
they were silently cut short; both now read through `src/lib/read-all.ts`.
